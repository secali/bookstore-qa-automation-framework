Defensa Técnica

Cuatro Pilares de la Solución

Argumentos técnicos estructurados para la defensa del framework ante el equipo evaluador.

01

Shift-Left y Validación Fuerte de Contratos

Validación de esquemas OpenAPI en tiempo de ejecución con Zod mediante SchemaRegistry. Detecta fallos de tipos, campos obligatorios omitidos y regresiones en menos de 15 milisegundos en la capa de servicios, antes de ejecutar pruebas en interfaz gráfica.

  • Envelope de error auditado: code, message y mapa anidado errors.
  • Independencia total del estado o estabilidad del frontend.
02

Arquitectura de Bloques y DataTables

Sustitución de la tradicional explosión de clases Page Object por un motor genérico dual: GenericHttpClient con soporte nativo de JSONPath y DataTables para validar múltiples campos en un paso, y ElementResolver para UI por accesibilidad.

  • Fábricas dinámicas aisladas en tests/fixtures/factories/ con Faker.
  • Curva de adopción inmediata para analistas QA y equipos mixtos.
03

Aceleración Híbrida y Cero Flakiness

Bypass de inicios de sesión repetitivos en navegador mediante precarga de JWT directamente en localStorage utilizando addInitScript de Playwright. Los datos previos se crean mediante llamadas REST ultrarrápidas y se validan visualmente en pantalla en un solo paso.

  • La inyección de sesión y el setup vía API evitan repetir pasos de UI en los flujos híbridos.
  • El hook limpia libros creados por API; el escenario UI borra su libro en un paso explícito.
04

CI/CD con Docker Local

El workflow carga bookstore-images.tar desde el checkout y espera la salud de /api/health. Para publicar el repositorio, el tar debe llegar al runner por un medio privado; incluirlo en un repo público expondría las imágenes.

  • Aislamiento estricto de datos preservando los libros semilla intactos.
  • Reportes consolidados HTML archivados automáticamente en GitHub Actions.

Diseño de Software

Comparativa Arquitectónica: POM vs OmniSpec

Evolución desde el patrón Page Object clásico acoplado hacia la orquestación atómica por componentes reutilizables.

Patrón POM Tradicional

Explosión de Clases y Deuda Técnica

  • Clases dedicadas: LoginPage, BooksPage, AddBookModal, DeleteConfirmModal.
  • Duplicación de selectores: Cada selector de botón o input se copia en múltiples métodos auxiliares.
  • Mantenimiento exponencial: Cualquier cambio en UI obliga a recompilar código TypeScript en Page Objects y Steps.
  • Steps huérfanos: Steps redactados como the user clicks the save book button on the modal intransferibles a otras páginas.
Arquitectura OmniSpec SDET

Motor Genérico y Composición Atómica

  • Page Objects y resolución reutilizable: Objetos de página ligeros junto a ElementResolver, con búsquedas semánticas (getByRole, getByLabel).
  • Resolución por contexto: When in the active modal, the user fills the form with data: funciona en cualquier modal.
  • DataTables nativas: Validación de múltiples campos en un único paso sin sintaxis repetitiva.
  • Menos código repetido: Los pasos genéricos cubren formularios y tablas comunes; los casos nuevos aún requieren validar su comportamiento y selectores.

Operaciones & DevOps

Despliegue Hermético con Docker y CI/CD

Instrucciones precisas para la ejecución local y en pipeline sin requerir acceso a registros públicos de contenedores.

Paso 1

Carga del archivo de imágenes local

Carga las imágenes del paquete local en el daemon Docker. MongoDB puede requerir descarga si no está cacheada.

docker load -i bookstore-images.tar
Paso 2

Orquestación de servicios

Inicia el entorno de pruebas en puertos aislados (API 5000, UI 3000, Mongo 27017).

docker compose up -d
Paso 3

Ejecución de la suite completa

Ejecuta la suite de 19 escenarios BDD con Playwright y Cucumber.

npm test
Paso 4

Generación del informe consolidado

Genera el reporte gráfico HTML con desglose de ejecución, tiempos y evidencias.

npm run report
